01설계 원칙

아래 다섯 가지는 구현 중 예외 없이 지킨다. 코드 리뷰에서 이 원칙을 어긴 변경은 반려한다.

RULE 1의존은 안쪽으로만 흐른다도메인은 아무것도 모른다. 안드로이드 SDK, 네트워크, DB, JSON 라이브러리를 도메인에서 import하는 순간 설계가 무너진다.
RULE 2바깥은 인터페이스로만 만난다DB·HTTP·시계·랜덤·파일까지 전부 포트(interface)로 뚫는다. 구현은 어댑터에만 둔다.
RULE 3테스트를 먼저 쓴다실패하는 테스트 → 통과하는 최소 구현 → 정리. 도메인과 유스케이스는 예외 없이 이 순서를 따른다.
RULE 4문구는 코드에 넣지 않는다사용자에게 보이는 모든 문자열은 리소스 키로만 존재한다. 서버는 문구가 아니라 코드를 내려준다.
RULE 5새 기능은 파일 추가로 끝낸다기능을 하나 더할 때 기존 파일을 여러 개 고쳐야 한다면 구조가 잘못된 것이다. 추가는 새 유스케이스 + 새 어댑터로.

1.1 왜 이 원칙인가

이 앱에서 바뀔 것이 거의 확실한 부분은 이미 드러나 있다. 과금 구조는 이미 세 번 바뀌었고(크레딧 도입 → 과금 시점 변경 → 크레딧 폐지), 거래 방식은 직거래에서 안전거래·문고리로 늘었다. 학교는 한 곳에서 여러 곳으로 늘어날 예정이고, 언어도 늘어난다.

공통점은 전부 "바깥"이 바뀐다는 것이다. 물건을 팔고 사는 핵심 규칙은 그대로인데 결제 수단, 저장소, 화면, 언어가 바뀐다. 그래서 핵심을 가운데 두고 바깥을 갈아끼우는 구조를 쓴다.

이 설계가 방어하는 실제 사고

  • 수수료율을 2%에서 3%로 바꿨는데 화면 다섯 곳을 고쳐야 하는 상황 → 정책은 도메인 한 곳에만 둔다
  • D1 용량 한계로 Postgres로 옮겨야 하는 상황 → 저장소는 포트 뒤에 있어 어댑터만 교체한다
  • 영어를 추가하려는데 하드코딩된 한국어가 200곳에서 나오는 상황 → 린트로 컴파일 단계에서 막는다
  • 결제 로직을 고쳤는데 어디가 깨졌는지 모르는 상황 → 도메인 테스트가 1초 안에 알려준다

02전체 구조

기술 선택과 근거
영역선택근거
앱 언어Kotlin 2.x순수 JVM 모듈로 도메인을 분리할 수 있어 헥사고날과 궁합이 좋다. 도메인 테스트가 안드로이드 없이 밀리초 단위로 돈다

DIHilt (Dagger)컴파일 타임에 의존 그래프를 검증한다. Koin은 빠르지만 오류가 실행 시점에 드러난다
비동기Coroutines + Flow표준. 포트 시그니처를 suspend로 두면 테스트에서 동기 실행으로 바꿔 끼울 수 있다
로컬 DBRoom오프라인 목록 캐시용. 어댑터 안에만 존재한다
서버Workers + HonoWrangler로 이미 배포 경험이 있다. Hono는 미들웨어가 얇아 유스케이스를 가릴 일이 없다
서버 DBD1 (SQLite)Worker와 같은 엣지에서 돌아 지연이 작고 운영이 없다. 파일럿 규모에 충분하다. 한계에 닿으면 어댑터만 바꾼다
실시간Durable Objects채팅방 하나가 객체 하나. 순서 보장과 연결 관리를 플랫폼이 해준다
이미지R2 + 서명 URL업로드가 Worker를 거치지 않아 CPU 시간을 쓰지 않는다
서버 테스트Vitest + workers pool모의 런타임이 아니라 실제 workerd에서 돈다. D1·R2·DO가 그대로 동작한다

03경량 헥사고날

정통 헥사고날은 레이어가 많고 파일이 불어난다. 학생 프로젝트 규모에서는 그 비용이 이득보다 크다. 그래서 세 겹만 쓴다.

겹있는 것없는 것테스트
Domain엔티티, 값 객체, 상태 전이, 계산(수수료·가격 검증), 정책안드로이드, 네트워크, DB, 코루틴, 날짜 획득, 로깅순수 JUnit. 가장 많고 가장 빠르다
Application유스케이스, 포트 인터페이스, 트랜잭션 경계프레임워크, DTO, SQL, Compose가짜 포트(Fake)를 끼워 시나리오 검증
AdaptersViewModel, Compose, Ktor 클라이언트, Room DAO, Hilt 모듈비즈니스 규칙 — 여기에 if가 쌓이면 도메인으로 옮긴다계약 테스트 · 화면 테스트 · 통합 테스트

05도메인 모델

도메인은 불변 데이터 + 순수 함수로 쓴다. 상태를 바꾸는 대신 새 상태를 반환하면, 테스트가 입력과 출력만 비교하면 끝나고 동시성 문제도 사라진다.

5.1 상태 전이를 타입으로 고정한다

// domain/escrow/Escrow.kt
enum class EscrowStatus { PAID, PLACED, CONFIRMED, DISPUTED, REFUNDED }

data class Escrow(
  val id: EscrowId,
  val itemId: ItemId,
  val buyerId: UserId,
  val sellerId: UserId,
  val price: Money,
  val fee: Money,
  val way: DeliveryWay,
  val status: EscrowStatus,
  val placedAt: Instant? = null
) {
  // 전이는 전부 메서드로. 바깥에서 status를 직접 대입할 수 없다
  fun markPlaced(at: Instant, proof: DropProof?): Result<Escrow> =
    when {
      status != PAID -> fail(EscrowError.NotPayable)
      way == DeliveryWay.DROP && proof == null -> fail(EscrowError.ProofRequired)
      else -> ok(copy(status = PLACED, placedAt = at))
    }

  fun confirm(): Result<Escrow> =
    if (status != PLACED) fail(EscrowError.NotConfirmable)
    else ok(copy(status = CONFIRMED))

  fun autoConfirmDue(): Instant? = placedAt?.plus(AUTO_CONFIRM)

  companion object { val AUTO_CONFIRM: Duration = 7.days }
}

이 형태가 주는 것

  • 불가능한 상태를 만들 수 없다 — 결제되지 않은 거래를 확정하는 코드는 컴파일은 되지만 Result.failure를 반환하고, 테스트가 그것을 고정한다
  • 규칙이 한 곳에 있다 — "7일 자동 확정"이 화면·서버·알림 세 곳에 흩어지지 않는다
  • 테스트가 1줄이다 — escrow.confirm()에 상태만 바꿔가며 호출하면 전이표 전체를 덮는다

5.2 값 객체로 단위 사고를 막는다

// 원과 크레딧, 원과 퍼센트를 섞어 쓰다 생기는 사고를 타입으로 막는다
@JvmInline value class Money private constructor(val won: Long) {
  operator fun plus(o: Money) = Money(won + o.won)
  fun percent(p: Int) = Money(won * p / 100)
  fun atLeast(m: Money) = if (won < m.won) m else this
  companion object {
    val ZERO = Money(0)
    fun won(v: Long): Result<Money> =
      if (v < 0 || v > 5_000_000) fail(PriceError.OutOfRange) else ok(Money(v))
  }
}

// 수수료 정책도 도메인에 둔다. 바뀌는 건 이 파일 하나뿐이다
object FeePolicy {
  private const val RATE = 2
  private val MIN = Money.won(500).getOrThrow()
  fun of(price: Money): Money = price.percent(RATE).atLeast(MIN)
}

Clock과 IdGenerator를 포트로 두는 이유

System.currentTimeMillis()와 UUID.randomUUID()는 테스트를 비결정적으로 만드는 가장 흔한 원인이다. "7일 뒤 자동 확정", "24시간 내 3회 제한", "10분 뒤 코드 만료" 같은 규칙은 시계를 주입할 수 없으면 테스트할 방법이 없다. 처음부터 포트로 둔다.

07유스케이스

유스케이스는 클래스 하나에 공개 함수 하나다. 이름이 곧 사용자의 의도이고, 파일 하나를 열면 그 기능의 전부가 보인다.

// application/usecase/escrow/ConfirmPurchase.kt
class ConfirmPurchase @Inject constructor(
  private val escrows: EscrowGateway,
  private val items: ItemRepository,
  private val notifier: Notifier,
  private val clock: Clock
) {
  suspend operator fun invoke(id: EscrowId): Result<Escrow> {
    val escrow = escrows.find(id) ?: return fail(EscrowError.NotFound)
    val confirmed = escrow.confirm().getOrElse { return fail(it) }  // 규칙은 도메인이
    escrows.save(confirmed)                                          // 저장은 포트가
    items.markSold(confirmed.itemId)
    notifier.push(Event.Settled(confirmed.sellerId, confirmed.price))
    return ok(confirmed)
  }
}

유스케이스에 if (status == ...) 같은 판단이 들어가면 도메인으로 내린다. 유스케이스가 하는 일은 순서를 정하는 것이지 규칙을 아는 것이 아니다.

단위 테스트에는 Hilt를 쓰지 않는다

도메인·유스케이스 테스트는 생성자에 Fake를 직접 넣는다. DI 프레임워크를 거치면 테스트가 느려지고, 무엇이 주입됐는지 읽기 어려워진다. Hilt는 실제 앱을 조립할 때와 계측 테스트에서만 쓴다.

화면은 상태를 받아 그리기만 한다. 판단이 없으므로 테스트가 쉽고, 디자인이 바뀌어도 로직이 따라 바뀌지 않는다.

// ui/home/HomeViewModel.kt
@HiltViewModel
class HomeViewModel @Inject constructor(
  observeItems: ObserveItems,
  observeHot: ObserveHotItems,
  private val toggleFavorite: ToggleFavorite
) : ViewModel() {

  private val filter = MutableStateFlow(ItemFilter.Default)

  val state: StateFlow<HomeState> =
    combine(filter.flatMapLatest(observeItems::invoke), observeHot()) { list, hot ->
      HomeState.Loaded(items = list, hot = hot)
    }
    .catch { emit(HomeState.Error(it.toUiError())) }
    .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), HomeState.Loading)

  fun onFavorite(id: ItemId) = viewModelScope.launch { toggleFavorite(id) }
}

10.2 D1 스키마 원칙

  • 모든 주요 테이블에 university_id. 단일 대학 파일럿이어도 처음부터 둔다 — 나중에 붙이면 전체 마이그레이션이다

  • 상태는 문자열 enum + CHECK 제약. DB가 불가능한 상태를 거부한다
  • 돈이 움직이는 모든 사건은 escrow_events에 append-only로 남긴다. 현재 상태는 파생값이다
  • 멱등성 키 테이블을 두고 결제·확정·환불 요청을 중복 처리하지 않는다

마지막 부분 인덱스가 "한 매물에 안전거래는 동시에 하나"라는 규칙을 DB가 강제하게 만든다. 애플리케이션 코드가 실수해도 데이터는 깨지지 않는다.

10.3 채팅 — Durable Object

  • 채팅방 하나가 DO 인스턴스 하나. 방 안에서는 메시지 순서가 보장된다
  • DO는 연결 관리와 브로드캐스트만 한다. 저장은 D1 어댑터를 통해서 한다
  • 앱이 끊긴 동안의 메시지는 재연결 시 since 커서로 동기화한다

10.4 이미지

  • 앱이 POST /v1/uploads로 서명 URL을 받아 R2에 직접 PUT한다
  • Worker는 바이트를 만지지 않는다 — CPU 시간과 요금을 아낀다
  • 학생증은 별도 버킷에 넣고 심사 승인 즉시 삭제한다. 접근은 전부 로깅한다

12TDD 전략

12.1 사이클

  1. Red — 실패하는 테스트를 먼저 쓴다. 테스트 이름은 한국어로 "무엇이 어떻게 되어야 하는가"를 적는다
  2. Green — 통과시키는 최소 구현. 예상되는 다음 요구를 미리 만들지 않는다
  3. Refactor — 중복을 지운다. 테스트가 초록인 상태에서만 구조를 바꾼다

12.3 테스트 대역은 Fake를 기본으로

Mock 라이브러리로 every { ... } returns ...를 늘어놓으면 테스트가 구현 세부에 묶인다. 리팩터링할 때마다 테스트가 깨지면 TDD가 짐이 된다. 그래서 포트마다 손으로 쓴 Fake를 하나씩 둔다.

// test-fixtures/FakeItemRepository.kt — 모든 테스트가 공유한다
class FakeItemRepository(initial: List<Item> = emptyList()) : ItemRepository {
  private val state = MutableStateFlow(initial.associateBy { it.id })
  var saveCount = 0; private set
  var failNext: Throwable? = null          // 실패 경로 테스트용

  override fun observeItems(f: ItemFilter) =
    state.map { it.values.filter(f::matches).sortedByDescending(Item::bumpedAt) }

  override suspend fun save(item: Item) {
    failNext?.let { failNext = null; throw it }
    saveCount++
    state.update { it + (item.id to item) }
  }
}

프로토타입의 가상 매물 16건을 FixtureItems로 그대로 옮긴다. 앱 테스트·서버 테스트·화면 스냅샷이 같은 데이터를 쓰면 화면과 로직의 기대값이 어긋나지 않는다.

한국어와 영어를 기본으로 하되, 세 번째 언어를 추가할 때 코드를 고치지 않는 것이 목표다.

14.1 누가 문구를 소유하는가

구분소유이유
화면 문구·오류 메시지앱서버 배포 없이 언어를 늘릴 수 있다. 오프라인에서도 문구가 나온다
푸시 알림서버 (사용자 언어 저장)앱이 꺼져 있어도 보내야 한다
이메일서버같은 이유
약관·정책문서 파일법률 검토 단위가 문서 전체다

14.2 키 규칙

<!-- res/values/strings.xml (ko) -->
<string name="home_search_placeholder">물건 이름이나 과목명으로 찾아보세요</string>
<string name="escrow_confirm_dialog_body">확정하면 %1$s이 판매자에게 넘어가고 되돌릴 수 없어요.</string>
<plurals name="offer_remain_count">
  <item quantity="other">오늘 %d번 더 제안할 수 있어요</item>
</plurals>

<!-- res/values-en/strings.xml -->
<string name="home_search_placeholder">Search by item or course name</string>
<plurals name="offer_remain_count">
  <item quantity="one">You can make %d more offer today</item>
  <item quantity="other">You can make %d more offers today</item>
</plurals>
  • 키는 화면_요소_상태 순서. 알파벳 정렬하면 화면별로 모인다
  • 한국어는 복수형이 other 하나뿐이지만 처음부터 plurals로 선언한다. 영어를 넣을 때 코드를 고치지 않기 위해서다
  • 문장을 "제안 " + n + "번"처럼 이어 붙이지 않는다 — 어순이 다른 언어에서 반드시 깨진다. 항상 위치 인자를 쓴다

14.3 도메인은 문구를 모른다

// 도메인은 오류 타입만 반환한다
sealed interface OfferError {
  data object TooHigh : OfferError
  data class LimitExceeded(val remainHours: Int) : OfferError
}

// i18n 어댑터가 문구로 옮긴다. 여기가 유일한 번역 지점이다
fun OfferError.toMessage(res: Resources): String = when (this) {
  TooHigh -> res.getString(R.string.offer_error_too_high)
  is LimitExceeded -> res.getQuantityString(R.plurals.offer_error_limit, remainHours, remainHours)
}

14.4 숫자·날짜·통화

  • 금액은 NumberFormat.getCurrencyInstance(locale)로 만든다. "원"을 문자열로 붙이지 않는다
  • 상대 시간("3분 전")은 RelativeDateTimeFormatter를 쓴다. 직접 만들면 언어마다 다시 만들어야 한다
  • 서버는 항상 UTC 정수 타임스탬프를 준다. 표시 시점에만 지역 시간대로 바꾼다

14.5 언어를 하나 추가하는 절차

  1. res/values-ja/strings.xml 추가
  2. 서버 messages/ja.json 추가 (푸시·이메일용)
  3. testTranslations가 빠진 키를 알려준다 → 채운다
  4. 끝. 코드 변경 0줄

이 구조를 깨는 흔한 실수

  • ViewModel에서 Resources를 받아 문구를 만들기 → 테스트에 안드로이드가 끌려온다. 상태에는 키와 인자만 담고 Compose에서 해석한다
  • 서버 오류 메시지를 그대로 화면에 띄우기 → 그 순간 서버가 문구 소유자가 된다
  • 한국어만 있는 상태에서 plurals를 생략 → 영어 추가 시 전부 다시 작성

15구현 순서

화면 단위가 아니라 수직 한 줄(도메인→유스케이스→어댑터→화면)씩 완성한다. 첫 줄이 끝나면 구조가 검증되고, 나머지는 같은 모양을 반복한다.

단계내용끝났다고 보는 기준
S0모듈 골격, Hilt 배선, 아키텍처 테스트, CItestArchitecture가 위반을 실제로 잡는다
S1수직 한 줄: Money·FeePolicy → ObserveItems → 목록 API → 홈 화면홈에 서버 데이터가 뜨고 도메인 테스트 20개가 초록
S2인증 2단계 (이메일·학생증)등급별 권한 차단이 화면에서 동작
S3매물 등록·상세·사진 업로드·전체보기사진을 올리고 목록에 반영
S4채팅 (DO + WebSocket)끊겼다 붙어도 메시지가 누락되지 않는다
S5가격 제안T-OFF 전 항목 초록
S6정산 계좌 · 안전거래 · 문고리T-ESC·T-SV 전 항목 초록, 대사 일치
S7영어 리소스 · 접근성 · 성능미번역 키 0, 글자 200% 통과

S1을 가장 공들여 만든다

첫 수직 한 줄이 이후 모든 기능의 본보기가 된다. 여기서 포트 이름, 테스트 이름, 폴더 위치, Fake 작성법의 관례를 정하고 README에 예시로 박아둔다. 이후 기능은 이 모양을 복사하면 된다.

16결정과 미결

16.1 결정 기록

ADR결정대안과 기각 이유
ADR-1안드로이드 네이티브 (Kotlin + Compose)React Native — PRD의 기존 선택이지만 안드로이드 전용이 되면서 이점이 사라졌다. 순수 JVM 도메인 모듈과 컴파일 타임 DI를 얻는 쪽이 요구하신 원칙에 더 맞는다
ADR-2HiltKoin — 설정은 쉽지만 오류가 실행 시점에 드러난다. 그래프 검증을 컴파일러에게 맡긴다
ADR-3D1외부 Postgres — 기능은 강하지만 엣지에서 연결 관리가 필요하고 운영이 늘어난다. 저장소는 포트 뒤에 있으므로 나중에 바꿀 수 있다
ADR-4서버는 메시지 코드만 반환서버가 문구 생성 — 언어 추가마다 서버 배포가 필요해진다
ADR-5Fake 우선, Mock 최소MockK 전면 사용 — 테스트가 구현에 묶여 리팩터링을 막는다
ADR-6도메인 규칙을 앱·서버 양쪽에 둔다서버만 — 화면이 서버 응답을 기다려야 버튼 상태를 정할 수 있다. 서버가 최종 판정자이되 앱은 즉시 반응용으로 같은 규칙을 갖는다. 두 곳의 테스트 케이스 표를 공유해 어긋남을 막는다
