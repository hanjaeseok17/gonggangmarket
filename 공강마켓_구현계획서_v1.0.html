01전제와 산정

1.1 전제

항목가정어긋나면
인원개발자 1명이 앱·서버·콘솔을 모두 담당—
1 MD하루 8시간 중 순수 개발 6시간. 나머지는 조사·회의·환경 문제학업 병행이면 실제 소요일은 1.5~2배
숙련도Kotlin·Compose·TypeScript를 이미 쓸 줄 안다학습이 필요하면 +30% (약 28 MD)
설계설계서 v1.0의 구조를 그대로 따른다구조를 즉흥으로 정하면 중반에 재작업이 생긴다
TDD도메인·유스케이스는 테스트 선작성생략하면 초반 20% 빠르고 후반 50% 느려진다
디자인프로토타입이 곧 시안. 별도 디자인 작업 없음새 시안이 오면 UI 공수 재산정
결제PG는 샌드박스까지만. 실계약·심사는 범위 밖실연동은 별도 협의 기간 필요

1.2 산정 방식

각 작업을 서버 · 앱 · 테스트 세 갈래로 쪼개 따로 잡고 합쳤다. 화면 하나는 평균 0.5~1.0 MD, API 하나는 0.3~0.5 MD, 도메인 규칙 하나는 테스트 포함 0.2 MD를 기준으로 삼았다.

  • TDD 계수를 따로 붙이지 않았다 — 테스트 작성 시간을 각 작업에 이미 포함했다. 테스트를 빼도 공수가 줄지 않는다고 본다
  • 버퍼 10 MD를 마지막에 따로 뒀다. 작업마다 여유를 조금씩 섞으면 그 여유는 반드시 사라진다
  • 0.5 MD 미만 작업은 인접 작업에 합쳤다. 쪼갤수록 정확해 보이지만 관리 비용만 늘어난다

1.3 구현 순서의 원칙

기능 단위가 아니라 수직 한 줄씩

"서버 전부 → 앱 전부"가 아니라 도메인 → 유스케이스 → API → 화면을 한 기능씩 끝까지 관통한다. 첫 줄(S1+S3 홈)이 끝나면 구조가 검증되고, 그 다음부터는 같은 모양을 반복하므로 속도가 붙는다. 반대로 서버를 다 만들고 앱을 시작하면 중반까지 눈에 보이는 결과가 없어 설계 오류를 늦게 발견한다.

오후  화면·통합 작업 (집중력이 덜 필요한 배선 작업)
마감  반드시 초록 상태로 커밋하고 끝낸다
      내일 할 일을 실패하는 테스트 한 개로 남겨둔다

13.2 작업 하나를 끝내는 절차

  1. 해당 작업의 테스트 케이스를 설계서 13장에서 찾아 먼저 작성 (없으면 새로 정의)
  2. 도메인 → 유스케이스 → 어댑터 → 화면 순으로 통과시킨다
  3. PRD의 대응 FR 번호를 커밋 메시지에 적는다 (FR-ESC-06 구매 확정)
  4. 완료 기준 열의 조건을 눈으로 확인한다
  5. 초록 상태에서 커밋·푸시

13.3 진척 관리

주기확인대응
매일완료한 작업의 MD 합계—
매주계획 대비 누적 MD, 남은 작업2주 연속 20% 이상 지연 시 범위를 줄인다. 야근으로 메우지 않는다
단계 종료완료 기준 전 항목, 테스트 초록미달이면 다음 단계로 넘어가지 않는다

진척은 "만든 화면 수"가 아니라 "통과한 테스트 수"로 센다

화면은 80% 완성처럼 보이기 쉽지만 테스트는 통과하거나 실패하거나 둘 중 하나다. 주간 보고에는 초록 테스트 수와 완료 기준 충족 여부를 적는다.
